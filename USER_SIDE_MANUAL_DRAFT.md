## A. CREATING A POST (Manual or AI-assisted)

**SUB-MODULE NAME (CREATING A POST)**  
**Font:** Times New Roman, **Size:** 20, **Style:** Heading 2

Users can create a forum post by entering a title, content, and optional image attachment. Anonymous posting may also be available depending on system settings.

Steps to create a post manually:
1. Open the Forum composer (click Create Post).
2. Enter a clear, descriptive title.
3. Enter the body of your post; use new lines for paragraphs and lists.
4. Optionally attach an image or file.
5. Choose a category and add relevant tags.
6. Click Publish to submit the post.

AI-assisted drafting (optional):

The forum also provides an AI-assisted draft generator that can produce a suggested post (title, category, body, tags, and estimated reading time). The backend endpoint powering this feature uses a locally configured Ollama model and returns structured JSON with the fields: `title`, `category`, `body`, `tags`, and `estimated_reading_time_minutes`.

How to use the AI generator:
1. With the composer open, click the **Generate with AI** button (or the AI suggestion control) when available.
2. Select a generation mode if prompted:
	- `alumni`: generate a topic using a random alumni-focused prompt.
	- `title_only`: produce or refine a title and full post body using the current title as input.
	- `content_only`: expand the existing body/content into a full post.
	- `both`: generate both title and body from provided inputs.
3. Review the generated draft inserted into the composer.
4. Edit the title, body, category, and tags as needed.
5. Click Publish to submit the final post.

Notes and administrator requirements:
- The AI returns a draft only — always review and edit before publishing.
- The feature requires Ollama to be configured by the site administrator (`application/config/ollama.php`). If the AI service is unavailable the Generate control may be hidden or return an error message.
- Generated drafts are returned as JSON by the server; the frontend composes them into the composer fields for user review.

## B. Edit Profile Information

**SUB-MODULE NAME (EDIT PROFILE INFORMATION)**  
**Font:** Times New Roman, **Size:** 20, **Style:** Heading 2

The primary Edit Profile flow uses a modal form. Editable fields include:
- First name and Last name (required)
- Degree
- Graduation year (numeric — validation enforced)
- Primary email (required)
- Alternate email (required and must differ from primary)
- Phone and Alternate phone (alternate must differ from primary)
- Profile image upload (jpg, jpeg, png, gif; max configured size ≈ 7 MB)

Notes on validation and behaviour:
- Graduation year must be a number; invalid values will show an error and re-open the edit modal.
- Alternate email and alternate phone must be different from the primary values — the controller rejects identical values.
- Image uploads are handled by the server and stored under `assets/uploads/alumni/`.

## I. Troubleshooting & Notes for Admins

**SUB-MODULE NAME (TROUBLESHOOTING & NOTES FOR ADMINS)**  
**Font:** Times New Roman, **Size:** 20, **Style:** Heading 2

- If image uploads fail, verify `assets/uploads/alumni/` permissions and PHP `upload_max_filesize` settings.
- The controller enforces simple server-side validation; client-side checks improve UX but do not replace server validation.
- Activity updates (e.g., 'Profile updated successfully') are surfaced using flash messages and modal re-open behaviour.

Developer references:
- Controller: `application/controllers/Profile.php` — endpoints: `index()`, `update($id)`, `update_job_info($id)`, `update_skill_info($id)`, `add_certification($id)`, `delete_certification($cert_id)`, `update_cover_photo($id)`.
- View: `application/views/user/profile.php` — UI, modals, and client-side scripts (Select2 init, modal triggers).
- Model: `application/models/user/Alumni_model.php` — persistence helpers: `get_alumni_by_id()`, `update_alumni()`, `get_certifications()`, `add_certification()`, `delete_certification()`.
